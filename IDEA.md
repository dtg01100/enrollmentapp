# ios-enroll

> **Goal:** Build the supervised-enrollment + restore subset of Apple
> Configurator for Linux admins who manage iOS fleets (SimpleMDM,
> Mosyle, custom MDM) on non-Mac workstations. Today the only way to
> supervise an iPad or iPhone from a non-Apple machine is the CLI of
> `pymobiledevice3`, which leaves GUI ergonomics, MDM profile
> plumbing, and firmware restore workflows to the operator.

This project is **not** an enterprise fleet-automation framework and
**not** an attempt to replicate every Apple Configurator feature
(Blueprint devices, AC2 pairing, Apple TV auto-install, etc., are
left out — if `pymobiledevice3` doesn't expose it, this tool doesn't
ship it). It is the smallest tool that covers the same two
workflows Apple Configurator ships on macOS:

1. **Prepare** — turn a fresh (or erased) iPad/iPhone into a
   supervised device with the org's identity cert, MDM enrollment
   profile, WiFi config, and chosen Setup Assistant panes skipped.
2. **Restore** — re-flash a device to a signed iOS version using a
   downloaded IPSW, including Recovery-mode devices that are
   invisible to usbmuxd.

Both today, both on Linux, both via a Typer CLI **and** a PySide6
GUI that share the same business logic.

---

## Why this exists

Apple Configurator only ships for macOS. Linux admins managing iOS
fleets (SimpleMDM, Mosyle, custom MDM on in-house servers) have no
GUI option — they wire together `pymobiledevice3` commands in shell
scripts or run a Mac VM just to do the supervised-enrollment + MDM
+ restore steps that AcC users take for granted.

The "Mac VM" workaround is a tax: another host to maintain,
another machine holding the supervising identity private keys, more
places for the cert chain to leak. This project is the alternative:
same two workflows, native on Linux.

## Explicitly out of scope

These are **not** part of the goal and should not be added unless
the project explicitly revises IDEA.md to include them (so future
contributors can see the cut-line at a glance):

- **Bulk / fleet operations.** No multi-device enroll, no MDM
  vendor API integration for pushing roles, no scheduled
  re-enroll. One device at a time. If you need fleet
  automation, you want something layered on top of `ios-enroll`
  (or a vendor tool like SimpleMDM), not this codebase's job to
  be that thing.
- **Web UI.** The CLI is the product for headless + scripted
  use; the GUI is a desktop convenience for the same operator.
  No HTTP service, no daemon mode.
- **macOS-specific features** Apple Configurator does that don't
  map cleanly to `pymobiledevice3` (AC2 pairing, Blueprint
  devices, Apple TV auto-install). If pymobiledevice3 doesn't
  expose it, this tool doesn't ship it.

## Target audience

The user is a Linux sysadmin who:

- Runs Linux on a workstation (Fedora/Ubuntu/Debian primary).
- Has an iPad or iPhone they want supervised and enrolled into
  an MDM (SimpleMDM, Mosyle, custom-hosted).
- Has the supervising identity (self-signed cert + private key)
  generated by this tool, exported from AcC, or otherwise
  produced out-of-band.
- Optionally, has WiFi creds or a WiFi `.mobileconfig` to push
  to the device before Setup Assistant so the device is online
  on first boot.

The audience is **not** an end user (no consumer-facing UX), not
a developer contributing to pymobiledevice3 (this composes it;
it doesn't patch it), not an enterprise with an Apple-only fleet
management team (this exists precisely because Apple Configurator
is the wrong shape for the Linux side of the same job).

## Today's coverage

The current tool (`v1.3.1`) implements the **Prepare** and
**Restore** workflows end-to-end. Everything below is shipped and
covered by tests.

### Prepare (supervised enrollment)

The 7-step Prepare Assistant, mirroring Apple Configurator's
workflow:

1. **Connect** to a normal-mode iPad/iPhone over USB. iOS 26
   untrusted-host failures are self-healed: the wrapper
   pairs-and-retries once before surfacing the original error.
2. **Activate** if `ActivationState == "Unactivated"`
   (via pymobiledevice3's `MobileActivationService.activate`).
3. **Apply cloud configuration** (`set_cloud_configuration`) with:
   `IsSupervised: True`, the org's supervisor cert chain, MDM
   server URL, optional `IsMDMUnremovable`, and the requested
   Setup Assistant skip list. If the device already has a
   cloud config that *matches* what we want, it proceeds
   (re-enrollment path); if it diverges, the operator must erase.
4. **Optional WiFi** install — either inline SSID/password or a
   full `.mobileconfig`. The WiFi install happens *before* the
   MDM profile so the device can reach the MDM server during the
   silent escalation. On a WiFi-only iPad (no SIM), this is
   mandatory for MDM enrollment to succeed.
5. **MDM profile install** with identity escalation
   (`install_profile_silent` w/ the org's keybag). The
   escalation challenge-response is retried up to 3× on
   `SignedRequestRejected`. The post-install `get_profile_list`
   verifies the MDM profile actually landed before reporting
   success.
6. **Reconnect** if the device disconnected during supervision
   apply (broken pipe / connection reset — the device reboots
   during the apply).
7. **Verify final state** by reading `IsSupervised` back from the
   device.

Setup Assistant panes are mapped through Apple's published
`device-management/skipkeys.yaml` (62 entries cross-checked
against pymobiledevice3's own defaults). Presets: `minimal`,
`standard`, `all` — see `src/apple_device_cli/enrollment/skip_panes.py`.

### Restore (firmware re-flash)

`ios-enroll device restore --ipsw <file> [--udid|--ecid] [--yes]`
runs `idevicerestore -e -y -P -C <cache>` and streams progress
lines to either the CLI or the GUI Restore tab. Mode-aware device
targeting:

- Normal mode → `-u <udid>` (only mode `-u` supports).
- Recovery / Restore / DFU mode → `-i <ecid>` (these devices are
  invisible to usbmuxd; the ECID is resolved from the iBoot USB
  descriptor's `srnm:[...]` / `ecid:...` fields, falling back to
  `irecovery -q`).
- Unknown mode → try `-u` first, retry `-i` once on "Unable to
  discover device mode".

A `ios-enroll device verify-ipsw --ipsw <file>` command streams
SHA-1 + SHA-256 over a downloaded IPSW and compares against the
hashes `ipsw.me` publishes for the matching device+build —
defense against a corrupt or attacker-substituted restore image.

A `ios-enroll device exit-recovery` command resets a stuck
Recovery-mode device to Normal via `irecovery --normal` (without
this, a device that gets stuck in recovery after a bad
supervised-enrollment apply needs a Mac + AcC to recover).

### Organizations + WiFi + MDM certs

`ios-enroll org ...` manages supervising-identity metadata:

- `create` / `generate` — write a fresh self-signed identity
  (2048-bit RSA, 5-year default validity, configurable via
  `--valid-days`).
- `import` — load a `.organization` file (Apple Configurator
  PKCS12 export), a directory already in our layout, or a zip
  of that directory.
- `import-mobileconfig` — load a `.mobileconfig` containing a
  `com.apple.mdm` payload and provision the org with the MDM
  server URL, check-in URL, and topic.
- `set-wifi` — copy a WiFi `.mobileconfig` into the org's
  directory so future enrollments auto-install it (with a
  default-Yes prompt on the org during enrollment).
- `show` / `list` — redact sensitive fields (MDM URL, cert
  subject) by default; `--json` returns raw for scripts.
- `delete` — rm-tree the org directory, gated on
  `_confirm_destructive_action` (TTY prompt or `--yes`).

The supervisor cert is 2048-bit RSA (industry-accepted minimum
for managed device MDMs — SimpleMDM and Mosyle accept it; bumping
to 4096 needs a CLI override, intentionally not added).

### Cross-platform notes

- `core/exceptions.py` and `core/redaction.py` are stdlib-only —
  importable from any platform without warnings.
- `orgs/manager.py` uses `os.scandir`-style file ops; the
  `fcntl` import is conditional (`msvcrt.locking` fallback for
  Windows) so the same Python module loads on every platform.
- The CLI is Typer + Rich; the GUI is PySide6 with QThread
  workers (each tab's workers are owned by a `WorkerPool` that
  gates the corresponding UI buttons while in flight and refuses
  close mid-operation).
- `pymobiledevice3` is the only "device" dependency. It already
  works on Linux + macOS + Windows; we don't fork it, we
  compose it.

## What's deliberately simple

- **No plugin system.** Workflows are 1-2 modules each; an
  abstract `Flow` base class would be more abstraction than
  there are flows to share between.
- **No internal queue / job system.** Restore runs in one
  subprocess call (or the GUI's QThread); Prepare runs in a
  single `asyncio.run()`. There is no second device being
  enroled at the same time, ever.
- **No database.** Org metadata is JSON on disk next to the
  cert/key; nothing needs ACID transactions. File locks
  (`msvcrt`/`fcntl`) prevent the only race that matters
  (concurrent `save_org` and `import_mobileconfig` for the same
  org name).
- **No remote/agent mode.** This is a single operator on a
  single workstation. There's nothing to dispatch over SSH.

## Non-goals

If a feature request would push us toward fleet-automation,
enterprise-policy authoring, or remote-management, that's a
different project. We stop here.
